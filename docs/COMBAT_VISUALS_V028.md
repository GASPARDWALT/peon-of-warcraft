# v0.2.8 combat visuals

The Warlock's saved basic move remains move ID 1. It is presented as **Wand
Strike**, with a small blue ranged projectile instead of the melee slash.
Its damage, unlimited charges and place in the turn sequence are unchanged.
The apprentice imp still contributes exactly 1 HP at the end of a complete
living combat round.

## Native changes

- A guarded temporary animation parameter selects the ranged branch only
  for an actual Warlock basic move. The original parameter is restored at
  the end of the complete animation. Other classes retain their own slash.
- The wand particle packet has the same 12-tile shape as the tested
  Firebolt/Shadow Bolt packet. A source-pointer guard swaps only that packet;
  neither move IDs nor animation tables receive new saved identifiers.
- Blue wand and violet shadow palettes change only the intended OBJ palette
  and retain the original palette source used by native restoration.
- The Warlock release pose and projectile share the physical wand tip
  `(32,52)`. The projectile stays above the player HUD. The imp launches from
  its own raised hand at `(80,44)`.
- Player back poses stage 576 bytes in the existing aligned WRAM6 scratch
  buffer, then use one CGB general DMA during VBlank LY 144..147. The LY
  interrupts are deferred from the visible LY140..143 prewindow, then LY
  is checked again to reject an IRQ race before waiting for LY144. The
  pending native VBlank interrupt runs immediately after the copy. Waiting
  with interrupts enabled inside LY144..147 was proven to starve under
  native audio work; this bounded prewindow avoids that hang.
  This replaces the old eight-tiles-per-frame upload and the initial HBlank
  trial, whose late STAT entry could finish after the portrait began.
  No LCD disable or new saved/scratch field is introduced. LCD-off/DMG
  requests retain the native loader; original registers and banks return.
- Tackle uses the documented native one-row target fix. Crystal's former
  two-row variant exceeded the hardware 10 OBJ-per-scanline limit and lost
  part of its impact. Move ID, damage and turn timing are unchanged.
- Totem and enemy-overflow uploads suspend BG-map refresh before selecting
  VRAM bank 1 and restore the bank before restoring the caller's map mode.

The bank-1 rank, totem, imp, bold-name cache and enemy-overflow allocations
remain separate. No new saved field, turn, move slot or equipment effect is
introduced.

## Reusable art

Run `python3 tools/build_peon_combat_assets_v028.py` before compiling.
It writes only `gfx/peon_combat_v028/` and
`references/generated/polish_v028/combat/assets/`:

- 44 native transparent PNG frames, matching sheets and transparent APNGs.
- Actual ROM particles: flame, nature, lightning, wind/frost, imp Firebolt,
  Shadow Bolt and Wand Strike.
- Four reusable 24×24 cast halos, clearly marked **source art only** in the
  manifest. They do not claim to appear in the ROM.
- All opaque colors come from RGB555 palettes; alpha is exactly 0 or 255.
  Enlargements use nearest-neighbor pixels, with no anti-aliasing.

The packet budgets are 16 native elemental tiles and two alternate
12-tile projectile packets. Old published assets and screenshots are never
regenerated by this tool.

## Validation

Run the following only after root freezes a matching ROM and symbol file:

```sh
PYTHONPATH=/workspace/toolchains/pyboy-preview python3 \
  tools/validate_peon_combat_v028.py --expected-sha ROM_SHA256
```

The validator records an ordinary fresh Warlock route, real follower and
inn transitions, combat, quest victory and a cold battery restart. Separate
temporary HP/loadout fixtures exercise the native controls and animation
interpreter for all currently authored class spells. They are explicitly
labeled diagnostics, rather than evidence of normal leveling/acquisition.

Checks cover consecutive complete actor poses and physical RGB555 pixels
while the actual actor is visible; native move-info windows and intentional
enemy reactions that temporarily convert the portrait to OAM are classified
separately. The actual hardware OAM count is checked on every visible scanline
(including offscreen-X objects, which still consume the hardware limit).
Additional checks cover
native OAM composites, all projectile phases, real launch/target positions,
HUD exclusion, immediate palette restoration, unchanged protected VRAM,
paired charges, canceled bag turn cost, the actual GDMA register writes/VBlank window/register and bank restoration,
and exactly one pet hit per round. PyBoy does not expose useful DMA-source
register readbacks; CPU values at the genuine store instructions are retained
instead, together with the resulting exact VRAM bytes.
Every proof records its exact ROM SHA; compilation and runtime results are
reported separately. Physical Chromatic behavior is still a hardware test.
